# Диаризация, участники и проверка качества

Диаризация группирует речевые интервалы по сходству голосов. Кластер Speaker N не равен подтверждённому человеку. Автоматическая оценка может объединять участников, особенно на длинной записи с похожими голосами или короткими репликами. Номер спикера не переносится между встречами.

Если число говорящих известно, передайте `speakerCount`, например 5. Используется кластеризация нормализованных embeddings с ограничением числа кластеров; она не строит плотную N×N spectral-матрицу для длинной записи. Это ограничение помогает разделению, но само по себе не доказывает, что каждый кластер соответствует одному человеку.

Для проверки запросите `outputs.segments` и `outputs.samples`. JSON содержит исходные речевые интервалы, реплики, длительность, число полученных кластеров, заданное ограничение и предупреждения. ZIP содержит до трёх коротких анонимных примеров каждого кластера и `index.json` с таймкодами. По примерам можно проверить редкий голос и дать человеку имя, не меняя технический распознаватель.

В рабочей папке исполнителя сохраняются `speaker-features.npz` и `asr-tokens.json`. Они привязаны к SHA-256 декодированного аудио, а ASR-кэш также к конфигурации движка. Повторная диаризация той же записи может менять число кластеров и пересобирать текст без повторного извлечения embeddings или ASR:

```sh
python3 diarize_ms.py <тот-же-вход> --speaker-count 5 --cache-dir <предыдущая-work-папка> --out <новый-транскрипт.txt> --json-out <новая-диаризация.json>
```

Первая обработка до внедрения кэша требует одного повторного прогона. Исходный результат следует сохранять отдельно. Кэши и голосовые примеры не включаются в Git и не копируются в bb-config.

Сопоставление людей и задач выполняет агент проекта по `references/project-people.md` навыка. Для смешанного кластера нужна привязка отдельных реплик/интервалов (`turnOverrides`), а не одно имя на весь Speaker N. Неподтверждённое имя или срок явно помечается; само число кластеров не подтверждает число участников.
