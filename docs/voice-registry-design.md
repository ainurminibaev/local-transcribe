# Узнавание участников встреч по голосу

Проект для согласования. Диаризация определяет, когда слышен голос в конкретной записи. Реестр связывает голос с человеком после явного подтверждения. Распознавание текста остаётся на GigaAM.

## Хранение и доступ

Единый реестр хранится на сервере BB в приватных данных модуля local-transcribe. Предпочтительный вариант — SQLite с шифрованием векторов и метаданных профиля ключом из защищённого хранилища сервера. База не входит в Git, артефакты задач, снимок настроек BB, обычные логи и экспорт транскриптов. Поиск изолирован между владельцами или рабочими пространствами BB. Постоянный профиль сохраняется после явного согласия участника или подтверждения владельцем, что такое согласие получено.

| Запись | Поля |
| --- | --- |
| Человек | Случайный ID, отображаемое имя, подтверждённые проекты, разрешение на поиск вне этих проектов |
| Образец | ID человека, идентификатор и версия энкодера, L2-нормированный эмбеддинг, качество, дата подтверждения |
| Подтверждение | Кто подтвердил, проект, дата и ссылка на задачу в пределах её хранения |
| Привязка встречи | ID задачи, номер кластера, ID человека, статус и происхождение решения |

Храним до пяти подтверждённых эмбеддингов на человека и энкодер. Звук в реестр не попадает. Пять секунд для прослушивания вырезаются из исходной записи по запросу, выдаются через закрытый доступ BB и удаляются по короткому TTL, например через 24 часа. При отсутствии исходного звука или чистого непрерывного фрагмента кластер остаётся анонимным. Для поиска вне проекта допускаются только явно разрешённые профили в пределах прав пользователя. Удалённые профили не восстанавливаются автоматически из резервных копий. В журнале можно сохранить сам факт удаления без имени и векторов.

## Подтверждение и исправления

1. На первой встрече проекта для подходящего неизвестного кластера BB спрашивает «Говорящий 1 — кто?» и даёт закрытую ссылку на 5 секунд записи. Пользователь выбирает существующего человека, указывает новое имя или пропускает вопрос. При добавлении профиля показываем, что сохраняется отпечаток, и отдельно спрашиваем, разрешён ли поиск в других проектах. Привязка подтверждается ответом.
2. На следующих встречах сверяемся сначала с подтверждёнными участниками проекта. Если уверенного совпадения нет, проверяем остальные разрешённые профили. Уверенный результат в подтверждённом проекте подписывается автоматически. При совпадении из другого проекта BB просит подтвердить личность и привязку к новому проекту. Пограничное совпадение показываем как «Имя?» пользователю с доступом к профилю. Если отрыв между кандидатами мал, оставляем «Говорящий N». В командные итоги спорное имя не подставляется автоматически.
3. «Говорящий 1 — это Анна, исправь» обновляет карту указанной встречи. Для переноса ошибочно зарегистрированного эмбеддинга запрашиваем отдельное подтверждение на том же примере. «Удали мой голосовой профиль» удаляет векторы и прекращает поиск по ним. Отдельно уточняем, нужно ли убрать имя из уже выданных файлов.

## Порог уверенности

Выбираем 2–3 независимых чистых фрагмента по 3–5 секунд. Исключаем перекрытия, края смены голосов, сильный шум и очень тихую речь. Используем косинусную близость только внутри одного пространства эмбеддингов. Оценка кластера — медиана по фрагментам. Для автоподписи хотя бы два фрагмента должны указать на одного кандидата.

| Решение | Условие |
| --- | --- |
| Автоподпись в проекте | Близость выше T_auto, отрыв от второго кандидата выше M, не менее двух согласованных фрагментов |
| «Имя?» | Близость выше T_review, второй кандидат заметно слабее, но автоподпись ещё не разрешена |
| Анонимный номер | Слабое или неоднозначное совпадение, противоречивые фрагменты или недостаточно речи |
| Кандидат вне проекта | Более высокие T_global и M_global, затем явное подтверждение нового проекта |

Стартовые ориентиры для пилота с ручной проверкой — косинус 0,80 / 0,70 и отрыв 0,08 для T_auto / T_review / M; для поиска вне проекта — 0,85 и 0,10. Это начальные значения, не вероятность совпадения. Пороги подбираем отдельно для каждой модели на встречах, отсутствующих в регистрационных образцах. Измеряем ложные подписи людей вне реестра, ложные совпадения между зарегистрированными, долю правильно подписанных людей и ошибки режима поиска вне проекта. Цель пилота — верхняя 95% граница доли ложных автоподписей не выше 0,5% на независимых отрицательных случаях. При нуле ошибок нужно около 600 таких случаев. При недостаточной выборке оставляем ручное подтверждение. [План оценки NIST SRE](https://www.nist.gov/system/files/documents/2021/07/12/2021_SRE_Evaluation_Plan_V5.pdf).

Один человек не присваивается автоматически двум пересекающимся кластерам. При конфликте обе подписи требуют проверки. Подтверждение имени не меняет границы диаризации и сохраняет пометки «говорящий неясен» на спорных стыках.

## Встраивание в текущую обработку

Из интервалов диаризации выбираются отрывки. Отдельный этап извлекает эмбеддинги и возвращает карту кластеров со статусами «подтверждено», «автоматически», «предположительно», «неизвестно». Исходные реплики, номера кластеров и таймкоды сохраняются. Исправление имени не требует повторного ASR. При недоступном реестре выдаются номера говорящих.

- **ModelScope.** Текущий CAM++ извлекает признаки для кластеризации. Для реестра лучше повторно извлекать признаки на чистых окнах по одному протоколу. Пространство включает модель, её версию, препроцессинг и размерность.
- **FluidAudio.** Swift-помощник сейчас публикует интервалы. OfflineDiarizerManager использует WeSpeaker и VBx. Для пилота можно оставить CAM++ общим энкодером сверки поверх интервалов FluidAudio и ModelScope. Профили сохранятся при смене диаризации. Если позже понадобится WeSpeaker для сверки, это отдельное пространство со своими порогами и пополнением профилей. [Документация FluidAudio](https://github.com/FluidInference/FluidAudio/blob/v0.18.4/Documentation/Diarization/GettingStarted.md).
- **Передача и сбои.** Исполнитель передаёт серверу только необходимые векторы, номера кластеров, таймкоды и оценку качества по каналу BB. Поиск и контроль доступа выполняются на сервере. Отмена, повтор доставки или повтор одного ответа не создают образец в реестре.

## Трудоёмкость

| Этап | Оценка |
| --- | --- |
| Реестр, доступы, удаление, привязки к проектам | 1–2 дня |
| Отбор отрывков, CAM++, сверка, карта говорящих | 1–2 дня |
| Подтверждение из BB, закрытый отрывок и исправления | 2–3 дня |
| Подготовка контрольных встреч и проверка порогов | 2–4 дня после получения подтверждённых примеров |
| Проверка совместимости с FluidAudio на Mac | 0,5–1 день после готовности диаризации FluidAudio |

Первый пилот — подписи после подтверждения в ModelScope, ориентир 4–7 рабочих дней. Автоподпись включается после замеров и проверки межпроектного доступа. FluidAudio проверяется отдельно и не блокирует пилот.
